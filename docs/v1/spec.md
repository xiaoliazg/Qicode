# Qicode V1（终端对话基座）Spec

## 背景

从空白开始构建 Qicode——一个 Python 实现的终端 AI 编程助手（对标 Claude Code）。V1 是它的对话基座：让用户先「聊起来」，为后续版本叠加 tool use、文件操作等 agent 能力打好地基。

模型后端对接本地以 **Ollama** 部署的 Qwen 模型（走其 OpenAI 兼容接口）；协议层同时交付 **Anthropic 原生适配器**——这正是原始需求里「支持 Anthropic Claude 和 OpenAI 两种 API 后端」的另一半：同一份代码既能接 OpenAI 兼容服务（Ollama、OpenAI 官方），也能接 Anthropic 原生协议的服务（Anthropic 官方 Claude、DeepSeek 的 Anthropic 端点）。Anthropic 链路的真机端到端已用 **DeepSeek 的 Anthropic 端点**跑通（见 AC18）；Anthropic **官方** Claude 侧因手上没有 key，仍只有单测覆盖。当前仓库无任何已有代码，全部从零搭建。

## 目标

- **G1 对话基座**：用户在终端启动 Qicode 后进入交互式 TUI，输入问题，回复以 SSE 流式逐字打印（不等全文生成完）。
- **G2 多轮记忆**：AI 记得当前会话内之前说过的话，上下文完整传给模型；支持清空历史重新开始。
- **G3 可配置的模型后端**：通过一份 YAML 配置文件管理模型供应商（V1 为本地 Ollama 部署的 Qwen；字段：`name` / `protocol` / `model` / `base_url` / `api_key` / `thinking` 可选 / `thinking_params` 可选）；启动时选择、运行中可切换，切换后历史对话保留。
- **G4 扩展思考**：支持模型的扩展思考模式（由配置项开启），思考过程以区别于正式回复的样式流式展示；思考开关对应的请求参数随协议可配置。原始需求点名的是 **Claude 的 extended thinking**，这里按协议通用化：Anthropic 侧即 Claude 的 extended thinking，OpenAI 兼容侧即服务端解析出的推理内容（reasoning）。
- **G5 可扩展 Provider 层**：模型接入抽象为按协议划分的统一接口，V1 交付 OpenAI 兼容与 Anthropic 原生两个适配器——正好覆盖原始需求点名的「Anthropic Claude + OpenAI」两条链路，未来继续新增协议时对话层零改动。

## 功能需求

### F1 启动与配置加载

- 启动时定位配置文件：默认读取用户主目录下的 `~/.qicode/config.yaml`，可用命令行参数指定其他路径覆盖。
- 配置文件为 YAML 格式，包含一个 provider 列表，每项含**五个必填字段**，另有**两个可选字段**（`thinking` / `thinking_params`）：
  - `name`：供应商标识名，方便区分多个配置
  - `protocol`：协议类型，V1 取值为 `openai_compatible`（对接 Ollama、OpenAI 官方等兼容服务）或 `anthropic`（对接 Anthropic 官方 Claude、DeepSeek 等原生协议服务）
  - `model`：指定模型
  - `base_url`：指定请求的地址
  - `api_key`：认证密钥，支持 `${ENV_VAR}` 环境变量引用
  - `thinking`：是否**主动请求**服务端开启扩展思考（可选，缺省 `false`）。注意它不承诺「关闭」：不发思考参数时服务端用自己的默认值，而部分后端（Anthropic 官方 Opus 5 / Fable 5、DeepSeek）默认就是开启思考的
  - `thinking_params`：思考开关对应的协议相关请求参数（可选）。**显式写出即生效，与 `thinking` 开关无关**；未写出时才由 `thinking` 决定发什么（`true` → 适配器默认值，`false` → 什么都不发）。适配器默认值：OpenAI 兼容侧 `chat_template_kwargs.enable_thinking`，Anthropic 侧 `thinking` 参数的 `type: adaptive` + `display: summarized`。**要确保关闭思考，须靠本字段明确表达**（Anthropic 侧为 `type: disabled`）
- 配置文件不存在时，提示用户并给出配置模板引导创建；配置文件存在但格式非法时，给出指出具体问题的错误信息，不崩溃。
- 启动时**不再弹出选择菜单**，直接以配置中的**第一个 provider** 进入对话（需要指定别的用 `-p/--provider`）。当前用的是谁，由启动横幅与输入区状态栏显示，随时可见。

### F2 交互式对话界面

- 进入内联式 TUI：提供带输入历史（上下键翻阅）、行编辑的输入框。
- 用户提交消息后，回复以流式（SSE）方式逐字追加打印，不等全文生成完毕。
- 对话以「用户消息 / 助手回复」交替的消息流形式呈现，历史消息保留在终端可向上翻阅。
- 助手回复渲染为带 Markdown 格式（代码块、列表、加粗等）的富文本。
- 流式生成过程中，用户可按 `Esc` 立即中断；已打印内容保留为该条回复，输入框恢复可用，会话继续。
- 进入对话时给出明确的界面标识（程序名、版本、当前 provider 与 model、工作目录），**且必须让用户一眼分辨出「已进入对话」而非「仍在选择 provider」**——这两种状态的混淆真实发生过。
- 输入态在底部显示当前 provider 与 model；`/model` 切换后随之更新。
- 生成期间、首个内容到达之前，显示「正在生成」指示与已等待秒数——用户要能区分「模型在算」与「卡住了」。
- 输入区以边框与提示符（`❯`）与输出区区分开。

### F3 多轮对话上下文

- 当前会话内所有历史消息（含助手回复）随每次请求完整发送给模型，AI 能引用之前说过的内容。
- 启用扩展思考的会话中，历史中的思考过程不参与回传（按模型 API 的规则处理，不产生非法请求）。

### F4 后端切换

- 运行中可通过 `/model` 命令查看当前后端并切换到列表中其他 provider。
- 切换即时生效：切换后新消息发往新后端，此前对话历史保留并继续发送。

### F5 扩展思考展示

- 当模型真的返回了思考内容时，思考过程以区别于正式回复的样式（如灰色斜体）流式显示，正式回复紧随其后。
- 思考内容是否出现，最终由「我们发出去的请求参数 + 服务端默认值」共同决定，不由 `thinking` 一个字段单独决定：`thinking: true` 且未写 `thinking_params` 用适配器默认表达；写了 `thinking_params` 则一律以它为准；两者都没有则不发参数，交由服务端默认值。
- 「如何向服务端表达思考」由 `thinking_params` 决定，各协议的默认表达不同，因此不写死在代码里。用户始终可以通过它表达「开启」「关闭」「按需」等具体语义。

### F6 斜杠命令

- `/clear`：清空当前对话历史，重新开始（后端配置不变）。
- `/model`：**不带参数**弹交互式选择面板，列出全部已配置的 provider（名称 · 模型 · 协议 · 思考开关），方向键选择、回车生效、Esc 取消；**带参数**（`/model <name>`）直接切到该 provider，不开面板，供习惯打命令或要脚本化时用。两种方式都即时生效、对话历史保留。
- `/exit`：退出程序（`Ctrl+D` / `Ctrl+C` 同样退出）。
- 输入无法识别的斜杠命令时，给出提示而非崩溃。

## 非功能需求

### N1 流式体验

- 首 token 到达后立即开始打印，逐 token 追加刷新，用户感知为「AI 在打字」，而非等待数秒后整段出现。
- 「逐字」是硬要求：每收到一个增量就立即重绘，不按帧率节流——用户看到的应当是一个字一个字地长出来，而不是每隔约 0.25 秒蹦出一整段（帧率只作为「流卡住时界面仍然活着」的兜底）。
- 流式过程中终端渲染不闪烁、不重排历史消息。

### N2 错误处理与健壮性

- 与模型服务通信失败（服务未启动、地址错误、超时、HTTP 错误、流中断）时，给出人类可读的错误提示（含原因与建议），会话不崩溃，用户可继续输入下一条消息重试。
- 错误信息中不得回显完整的 API key。
- 非法输入（空消息、未知斜杠命令、格式错误的配置文件）都有明确提示，不抛裸异常堆栈给用户（调试信息可另存/可选输出）。

### N3 安全

- `api_key` 支持 `${ENV_VAR}` 环境变量引用，敏感场景可不落盘明文。
- 程序不在日志、报错、界面中泄露 API key；配置文件读取失败或权限异常时提示清晰。

### N4 可移植与运行环境

- 纯 Python 实现，运行在 macOS 与 Linux 的常规终端中，无系统级依赖（不依赖特定终端模拟器、不需要 root）。
- Python 版本要求明确声明，依赖清单完整，克隆后按说明可一次性安装成功。

### N5 可维护性

- 模型接入层按协议抽象：V1 交付 OpenAI 兼容与 Anthropic 原生两个适配器，接口设计保证继续新增协议时，对话层与 TUI 层零改动。
- 模块边界清晰（配置 / 模型接入 / 对话管理 / 界面 各司其职），关键逻辑有注释说明。

## 不做的事

- **不做 agent 能力**：无 tool use、不读写本地文件、不执行 shell 命令、不做代码编辑。纯对话，模型只有「说话」这一种输出方式。
- **不实现 OpenAI 兼容与 Anthropic 原生之外的协议**：这两条链路 V1 交付；其余协议（如 Gemini 原生）仍按协议抽象预留，需要时新增适配器文件即可，上层零改动。
- **不做跨会话持久化**：对话历史仅存在于内存，退出即丢；不做会话存档、恢复、导出。
- **不做多用户 / 认证授权**：单用户本地工具，无账号体系、无权限管理。
- **不做 GUI / Web 界面**：只有终端 TUI。
- **不做生成中修改提示**：只能整体打断重来，不能在生成中途往消息里插入补充文字。
- **不做系统提示词配置**：V1 不开放自定义 system prompt 的入口，使用内置默认值。
- **不做 i18n**：界面文案默认中文。
- **不做自动更新 / 打包分发**：源码运行即可，不构建安装包。

## 验收标准

### 对应 F1 启动与配置加载

- **AC1** 在配置文件中写入两个 provider（其一指向本地 Ollama，另一个故意写错地址），启动后**直接进入对话界面**（不再弹选择菜单），当前使用的是配置中的第一个；启动横幅与状态栏都能看到当前 provider 与模型。
- **AC2** 删除/重命名配置文件后启动，程序不崩溃，给出「配置不存在」提示和模板引导；按提示补建配置后再次启动正常。
- **AC3** 将配置文件中某字段的 YAML 语法写坏（如冒号缺失），启动时给出指向具体行/字段的问题提示，而非裸异常堆栈。
- **AC4** 配置中 `api_key: ${QWEN_API_KEY}`，未设置该环境变量时启动给出明确提示；设置后正常发起请求。

### 对应 F2 交互式对话界面

- **AC5** 发送一条问题后，回复在模型首 token 到达时即开始逐字打印，而非等待数秒后整段出现；判定口径是「字符连续增长」而非「按固定节奏成段跳变」；打印过程不闪烁、历史消息不重排。
- **AC6** 输入框支持上下键翻阅本会话已发送的消息，支持退格、方向键等常规行编辑。
- **AC7** 让模型输出一段含代码块的回复（如「写一个 Python 快速排序」），代码块以等宽高亮的富文本呈现，而非裸文本。
- **AC8** 在一条长回复生成过程中按 `Esc`，打印立即停止，已打印内容保留为该条回复，输入框恢复可用，且后续对话能正确引用这条被截断的回复。

### 对应 F3 多轮对话上下文

- **AC9** 第一轮告诉 AI 一个个人信息（如「我叫居居」），几轮无关对话后问「我叫什么」，AI 正确回答「居居」。
- **AC10** 在启用 thinking 的 provider 下完成多轮对话，第二轮请求不报错（历史中的思考内容按 API 规则处理，未产生非法请求）。

### 对应 F4 后端切换

- **AC11** 用第一个 provider 聊几轮后执行 `/model <第二个的名字>` 切换过去，再问「我们刚才聊了什么」，AI 能复述切换前的内容（历史保留）。
- **AC12** 切换到指向错误地址的 provider 后发消息，得到可读错误提示，会话仍存活，`/model` 切回正确后端后可继续对话。

### 对应 F5 扩展思考展示

- **AC13** 在 `thinking: true` 的 provider 下提出一个需要推理的问题，思考内容以区别于正式回复的样式（灰色/斜体）先行流式显示，正式回复紧随其后。（验证：**已真机验证**——DeepSeek 的 Anthropic 端点，`thinking: true`。思考内容先完整流式输出、正式回复紧随其后；转义序列比对确认思考行带 dim + italic、正文行不带。Anthropic **官方** Claude 仍未验证，手上没有官方 key。）
- **AC14** 对某个 provider **显式关闭**思考（`thinking_params` 写明关闭参数）后提问，界面上无任何思考块展示——**哪怕该后端本身默认就是开启思考的**。（验证：**已真机验证通过**——DeepSeek 的 Anthropic 端点，`thinking: false` + `thinking_params: {type: disabled}` → 实测 0 个思考字符、界面无思考块；同一后端、同一道推理题在只写 `thinking: false` 时有 187 个思考字符，对比成立。更早的写法下这条 AC 不成立，原因是 `thinking: false` 只意味着「不发参数」，而用户写的关闭参数又会被静默丢弃——该缺陷已于 2026-09-22 修复，详见 task.md T14。）

### 对应 F6 斜杠命令

- **AC15** `/clear` 后提问「我刚才问了什么」，AI 表示不知道（历史已清空）；后端配置保持不变。
- **AC16** `/exit`、`Ctrl+D`、`Ctrl+C` 三者均能正常退出程序，退出码干净（无异常堆栈）。
- **AC17** 输入 `/foo` 等未知命令，给出「未知命令」提示，会话继续。

### 对应 G5 / N5 协议扩展

- **AC18** 配置一个 `protocol: anthropic` 的 provider，启动后可正常列出并选中；对其发起对话，回复以与 OpenAI 兼容链路**完全一致**的方式流式逐字打印，且 `/clear`、`/model`、`Esc` 打断、`/exit` 行为一致——即上层代码未因新增协议而改动。（验证：**已用真实服务跑通**——DeepSeek 的 Anthropic 端点。列出/选中/多轮对话/思考开关/跨协议切换历史保留/Esc 打断/退出均与另一条链路无差别，退出码 0；单测另以 mock 覆盖事件翻译与错误翻译。**仍未验证**：Anthropic 官方 Claude——无官方 key，该厂商特有的行为（如 `refusal` 收尾）仍只有单测覆盖。另外确认了一件顺带的事：我们发往 Anthropic 协议的默认 `thinking` 参数 `{type: adaptive, display: summarized}` 被兼容服务接受，`display` 也确实生效）
- **AC19** 在 provider 上写自定义 `thinking_params` 后发起请求，实际发出的请求体里出现该参数；未写该字段时使用适配器默认值。（验证：单测断言请求体，不依赖真实服务）
- **AC20** `protocol` 写成既非 `openai_compatible` 也非 `anthropic` 的值（如 `gemini`），启动时给出「暂不支持」的明确提示，而非崩溃。

### 对应 F2 的界面呈现（T16 补记）

- **AC21** 进入对话时**先把整屏擦干净**——既清可见区，也清终端回滚缓冲（向上翻页不能翻出启动前的命令行），然后才在顶部落下界面标识（程序名、版本、当前 provider 与 model、工作目录），且从中能明确判断「已经进入对话」；终端宽度收窄到 60 列时不破版（信息可截断，不得错位）。
- **AC22** 输入态底部显示当前 provider 与 model；`/model` 切换后底栏内容随之更新。（说明：生成期间底栏不可见——生成态不归 prompt_toolkit 管，工具栏只活在输入态。这**不是**「钉住底栏必须上全屏、会牺牲回滚历史」：那条说法已被实测证伪，`bottom_toolbar` 与自绘输入区都写在正常屏幕上，「钉底」与「往上翻能看历史」同时成立，详见 plan.md 模块四附 ③。）
- **AC23** 提交消息后、首个内容到达前，界面显示「正在生成」指示与递增的秒数；首个增量到达时**无缝切换**为逐字正文，无闪烁、无重复行。用一个有明显首 token 延迟的提问（如让本地 Ollama 做一道需要思考的题）即可观察。
- **AC24** 输入区有边框与 `❯` 提示符；做完本条后必须重跑 AC8（Esc 打断）与 AC16（三条退出路径）——边框改的是输入层，与 termios 切换、Ctrl+C 处理在同一片区域（T6 的踩坑就在此处）。

### 对应 F6 的模型选择（T17 补记）

- **AC25** 在对话中敲 `/model` → 弹出模型选择面板（**面板贴屏幕底部出现，不把上方对话内容顶上去**），列出全部已配置的 provider 及其模型与思考开关；方向键可移动选中项，回车切到该项并提示「已切换到 x（对话历史保留）」，Esc 取消且不发生切换。`/model <name>` 则不开面板直接切换，名字不存在时给出提示且不崩。切换后输入区状态栏随之更新（AC22）。
